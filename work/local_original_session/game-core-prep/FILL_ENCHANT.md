## 기존 소비 계약과 경계

`world_feature_items._world_enchant_use`는 소유한 주문서/대상 UID를 조회하고 실제 대상의 종류·현재 레벨을 `EnchantTarget`으로 넘긴다. 기존 caller는 아이템 행의 안전값이나 일반 주문서 eligibility를 전달하지 않는다. 이번 강화표 등록으로 `world_enchant`의 known row 조회가 안전값을 제공하므로 숫자 안전값이 있는 신규173종은 기존 경로에서 정책 대상이 된다. ID25는 무기, ID26은 방어구 주문서이며 등급0/1/2는 별도 인스턴스 입력이다.

일반·축복은 현재 레벨이 안전값보다 작을 때 성공100%다. **안전값과 같은 레벨에서 다음 단계로 가는 시도부터 확률**을 적용한다. 저주는 안전 검사보다 먼저 처리하며 현재 레벨>-7이면-1, <=-7이면 파괴한다. 축복 성공 시 레벨<=2는 +1/+2/+3이32/44/24%, 레벨3~5는 +2/+1이49/51%, 레벨>=6은+1이다. 성공·유지·파괴는 각각 주문서1장을 소비하고 거절은 소비하지 않는 기존 계약을 유지한다.

## 검증 결과와 제한

- JSON을 재파싱하고 장비219행의 중복0·등록 누락0·미등록 참조0, 명칭/종류/안전값 불일치0을 확인했다. null16종의 공식 금지 원문과 숫자203종의 안전값을 대조했다.
- 기존 확률·주문서·전투 정책은 변경 전과 동일하며 기존 장비29행은 완전 동일하다. 기존103행은 안전값과 그 출처 설명만 바뀌었다. 주문서25/26×등급0/1/2의6조합을 보존했다.
- JSON 식을 대상으로 존재하는 종류/안전값5조합, 시도 전 레벨-8..20에서 성공·유지·파괴가 각각0..100이고 합계100인지 검사했다. 안전 직전/안전값·레벨8/9·12 경계와 축복 상승량 분포 합계100을 확인했다. 이는 데이터식 계산 검사이며 게임 함수·RNG 실행 시험은 아니다.
- `python -X utf8 -B -c "from tools.local_original_session import game_data; d=game_data.load_m1(); print(len(d.items))"` 성공: 아이템279종, 그중 장비219종. 이 로더는 강화표를 직접 읽지 않으므로 강화 JSON의 별도 파싱·참조 검사를 함께 수행했다.
- 게임·서버·봇·포트·패킷·저장 mutation·실제 강화 함수 시험은 실행하지 않았다. 원본 화면·입력·결과0967 enum/등급 wire·저장/복원·실플레이 동등성은 이번 검증 범위 밖이다. 기존 [ENCHANT_USE_EVIDENCE](ENCHANT_USE_EVIDENCE.md)의 원본 미확정을 해소한 작업이 아니다.

Python 변경 없이 이번 데이터 연결은 가능하다. 후속으로 코드 변경이 허용될 때 필요한 정리는 다음 두 항목이다. 현재 범위에서는 수정하지 않았다.

1. `world_enchant_tests.py`의 `test_known_m1_safety_is_per_item`는103의 옛 안전값0을 기대한다. 공식4로 기대값을 바꿔야 하며 현재 그대로 실행하면 해당 기대값이 실패할 수 있다. 해당 시험을 실행하거나 수정하지 않았다.
2. 공식 금지와 진짜 안전값 미확정을 다른 사유로 표시하려면 `world_enchant.propose_enchant`가 known row의 `normal_scroll_eligible:false` 또는 명시 금지 상태를 안전값 null 검사보다 먼저 읽도록 해야 한다. 현재 금지 차단 자체에는 변경이 필요 없으며 새 wire 의미를 확정할 근거도 아니다.

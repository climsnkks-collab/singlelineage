# broker 월드·launcher 키트 변경 읽기 전용 리뷰

2026-10-26 현재 미커밋 작업 트리 기준. 다른 작업자의 동시 수정이 있으므로 아래 줄 번호는 리뷰 당시 기준이다. 제품 파일 수정·커밋·게임·서버 실행은 하지 않았다. 아래 4건은 **코드 경로를 확인한 정적 발견**이며 실제 패킷·화면 재현 결과가 아니다.

## 1. [P2] 새 물약 효과 뒤에 과거 HP·속도 알림을 전송한다

- **근거:** `tools/local_original_session/broker.py:4161–4164, 4173–4174`는 heal/buff 적용 직후 새 응답을 보낸다. 기존 outbox는 `:4216–4219 → :4238–4239`에서 나중에 전송한다. `:4313–4333`은 수신과 월드 이벤트가 함께 준비되면 수신을 먼저 처리한다. `world_visibility.py:142–153, 245–246, 266–272`에서 이전 피격/회복·버프 만료 알림이 큐에 남을 수 있다.
- **재현 조건:** NPC 피격 HP20 알림이 대기한 상태에서 회복 물약 요청을 처리한다. 새 HP25 응답 뒤에 기존 HP20 응답이 도착한다. 헤이스트 만료 알림이 대기한 상태에서 다시 헤이스트를 사용하면 새 가속 뒤에 과거 속도 초기화가 도착한다.
- **영향:** 서버의 현재 HP·속도와 클라이언트에 마지막으로 전달된 값이 달라진다. 화면 수치·이동 속도에 나타나는 구체 증상은 실행 미확인이다.
- **최소 수정:** 같은 `dispatch_now` 호출 안에서 기존 outbox를 drain하고 효과를 적용하여, **기존 알림 → 인벤토리 변경 → 새 효과** 순서로 기존 `_world_send`에 넘긴다. 먼저 별도의 flush를 await하는 방식은 그 대기 중 새 알림이 쌓일 수 있다. 공격의 `world_visibility.py:361`이 기존 알림을 함께 반환하는 선례다.

## 2. [P2] 수동 AddInventory를 먼저 완료하면 키트 초기 동기화가 영구 차단된다

- **근거:** `launcher.py:4210–4218`은 `_inventory_auto_selection is None`이면 초기 장비 준비를 건너뛴다. 수동 AddInventory는 `:2164–2165`에서 이 값을 None으로 만들며, 키트 확인 성공 경로 `:2788–2798`도 값을 채우지 않는다. 이미 지급한 경우 `:2532–2533` 때문에 자동 claim이 다시 생기지 않는다. `broker.py:633–642`는 초기 동기화 전 Use 효과를 생략한다.
- **재현 조건:** 자동 지급 claim보다 먼저 공개 수동 AddInventory 요청을 완료한다. 같은 선택 세대에서 CLIENT_CONFIRMED가 되어도 `_equipment_prepared`는 계속 False다.
- **영향:** 아이템은 보이지만 장비 초기 동기화와 장착·물약 사용 효과가 같은 선택 세대에서 계속 실행되지 않는다.
- **최소 수정:** 자동 요청 출처 marker 대신, 같은 generation의 실제 AddInventory 확인 완료·대기 상태를 기존 준비 조건에 사용한다. 수동 성공도 동일하게 준비를 진행하되 확인 중에는 기존 대기를 유지한다.

## 3. [P2] 월드 사망 뒤 이동과 효과 없는 물약 소비가 저장된다

- **근거:** world 전용 사망·리스타트는 `broker.py:775–779, 1429`에서 지원하지만, 정상 행동 차단 `:798–801`은 `_player_life_broker`가 있는 경우만 적용된다. 이동 `:577–588`과 owner 확인 `:2302–2323`은 월드 사망을 확인하지 않아 `movement.py:327–334`의 위치 저장까지 진행한다. 물약도 `item_equipment_effect.py:418, 438–448`에서 bound 여부만 보고 수량을 먼저 저장한다. `world_combat.py:328–329`는 죽은 PC에 회복량 0을 반환한다.
- **재현 조건:** world_policy 사용·player_life_policy 미사용 구성에서 NPC 치명타로 HP0이 된 뒤, Restart 전에 유효한 4E2B 또는 0960이 처리된다. 사망 직전 전송된 입력이 대기 중인 경우에도 성립한다.
- **영향:** 죽은 PC의 좌표가 영구 변경되거나 물약이 회복 없이 영구 차감된다. 실제 클라이언트의 해당 입력 도착 빈도는 미관측이다. 공격은 `world_visibility.py:331–334`에서 이미 사망을 거절하므로 행동별 생명 경계가 불일치한다.
- **최소 수정:** 기존 정상 행동/사망 분기에 현재 월드 생명 상태를 연결하여 이동·Use의 상태 변경을 중단한다. 요청 도중 await가 있는 경로는 마지막 저장 전에도 같은 생명 상태를 반영해야 한다. 단순 owner 실패로 바꾸어 전체 세션 종료를 유발하지 않도록 한다.

## 4. [P2] 마을 복귀 저장 실패 시 복귀 의도를 잃고 사냥터에서 최대 HP로 재진입한다

- **근거:** `broker.py:4104`가 저장 전에 `_world_respawn`을 pop한다. `:4110–4116`은 위치 저장 예외를 삼켜 False를 반환하고, 선택 경로 `:512–519`는 반환값을 무시하여 이전 좌표를 복원한다. 이미 `_world_leave :4270–4275 → world_combat.py:295–301`에서 사망 PC의 다음 HP는 최대값으로 바뀐다.
- **재현 조건:** 사망 → Restart → 재선택 때 positions.json 읽기는 가능하지만 `movement.py:168`의 교체가 일시적으로 실패한다. 예를 들어 다른 읽기 핸들이 삭제 공유를 허용하지 않는 경우다. 장애 주입은 실행하지 않았다.
- **영향:** 이전 사냥터 좌표에서 최대 HP로 재진입하며 pending이 없어 다음 선택·종료에서도 마을 복귀를 재처리할 수 없다. 조용히 실패하는 복구 경로다.
- **최소 수정:** town commit 성공 또는 이미 town 좌표인 경우에만 pending을 제거한다. 복귀 저장 실패는 선택의 기존 오류 경로로 전달하여 이전 좌표의 정상 진입으로 승격하지 않는다. 기존 PositionStore의 불확정 저장 결과·CAS 경계는 유지한다.

## 지연 가능성 — 추론, 실측 없음

`broker.py:4238–4239`는 전체 outbox를 꺼내고 `:4082–4085`는 모든 chunk를 연속 송신한다. `:4323`에서 이 작업을 기다리는 동안 read_task가 완료되어도 수신 처리는 뒤로 밀린다. 각 프레임은 `:3666`의 checkpoint, `:3832`의 drain, `:3853`의 owner/source 확인을 순차 수행한다. **알림 n개 × 프레임당 처리 시간만큼 입력이 대기하는 구조**는 확인했지만 실제 backlog·시간은 측정하지 않았다. 최소 수정 방향은 기존 chunk 경계에서 준비된 입력에 실행 기회를 주도록 송신을 나누는 것이다. 이때 발견 1의 과거 알림 선행 순서를 보존해야 한다. 현재 launcher의 `verify_sources :888–894`는 handle 확인이므로 매 프레임 39MB 해시를 수행한다고 판단하지 않았다.

## 확인 범위·검증

- `world_policy`, `_world_flush`, `_world_attack`, `_world_edge_fallback`, `_world_leave`, `_frames_for` 월드 분기, 키트 지급/장착/물약/헤이스트, 사망/Restart 및 launcher 연계를 검토했다. 실제 world callback은 동기 함수이고 확인한 잠금 순서는 row → world다. 반대 방향 row 잠금 획득에 의한 확정 교착은 찾지 못했다. `_world_leave` 예외 삼킴은 정상 입력에서 발생하는 예외와 피해를 입증하지 못해 별도 결함으로 올리지 않았다.
- 재사용 근거: `game-core-prep/GAME_CORE_DESIGN.md`의 단일 상태 소유·사망 입력 정리 계약, `REUSE_TABLE.md`, 기존 `integration-1/repeated-player-life-serial316-v1/API.md`의 선택 퇴역/원 Life 정리 경계를 참조했다. 새 역분석은 하지 않았다.
- 실행: 프로젝트 루트에서 `"C:\Users\Chansol\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe" -X utf8 -B -m tools.local_original_session.world_tests` → **6 tests, OK**. 순수 엔티티·스케줄러·runtime 시험이며 위 broker/launcher 결함을 실행 재현한 시험은 아니다.
- broker 시험·loopback·실제 게임/서버는 실행하지 않았다. 원본 화면·입력, 실제 세션 종료, 장애 주입, 지연 시간은 확인하지 못했다. 제품 파일과 다른 작업자의 변경은 수정하지 않았다.

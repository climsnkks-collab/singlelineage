## Primitive contract

`ui_owner_mailbox.hpp` has one process-lifetime singleton and one outstanding immutable value request. Request contains only monotonic nonzero uint64 sequence, the single typed `Kind::Checkpoint`, and a tag bounded to 0..65535. No request contains a model, panel, command callback, receive-buffer pointer, game message/opcode or input action. Publish copies the request under a short SRW lock, posts a zero-payload private WM_APP wake to this implementation's own HWND and returns Queued only if PostMessage succeeds. Queued is not OwnerProcessed. Receipt remains until the publisher observes it and acknowledges its exact completed sequence; the next accepted request may replace the previous receipt. Busy, invalid/replayed sequence, unknown kind, oversized tag, missing endpoint, revoked and wake-failure results are distinct. No retry/reconnect or unbounded queue exists.

The existing validated owner `BeforeUi` scope (recorded uiThread, nonnegative hook code, PM_REMOVE and actual MSG) admits the first AfterUi attach. Negative/nonremoved callbacks do not attach this primitive. Attach verifies that current native thread equals the recorded owner, pins the native module before registering any callback, registers its private class once, and creates a zero-style `HWND_MESSAGE` window. Class collision fails rather than adopting another window procedure. CreateWindowEx returning the actual HWND records the dispatcher creation receipt and native owner/create thread. No top-level window, controls, visibility, focus, activation or thread-input attachment are requested. The registered class and module stay resident for process lifetime; there is no unload promise.

Both genuine owner AfterUi service and the private window procedure can consume an admitted Checkpoint. They only record OwnerProcessed; no selected UI operation runs. A wake message supplies no authority or pointer: without an already admitted request, it has nothing to execute. The native message-only endpoint remains independently dispatchable after the original observation hook is removed, while the original owner loop continues to pump messages. It is not a guarantee that an owner loop will ever run again.

## Revocation and actual native close

Existing Selected/Close/final Revoke now also permanently revokes mailbox admission under the same mailbox lock used by Publish. A pending request becomes CancelledBeforeOwner, so a later wake cannot process it. Off-thread Revoke posts only the private wake and never calls DestroyWindow, waits, touches controls or reports a completed owner close. If the owner does not run, the actual HWND/state/class/module are retained and phase stays UnknownRetained. Neither timeout, worker Join, absent hook, IsWindow, process exit nor enqueue is converted into Closed.

Terminal AfterUi revokes and invokes owner close before returning to Forward. For the race where manual_move becomes terminal after AfterUi's check, the actual Forward-selected detach calls `BeforeUnhook`: it revokes mailbox admission and runs owner close immediately before the original UnhookWindowsHookEx. It forwards the original unhook return/error and does not change CallNextHookEx or manual_move's detach policy. An absent/wrong owner or failed DestroyWindow retains UNKNOWN; it does not invent a receipt or claim to prevent original teardown.

Owner close withdraws the published endpoint under lock before invoking synchronous DestroyWindow outside that lock. A Closed dispatcher receipt requires **actual DestroyWindow return TRUE plus this window's WM_NCDESTROY during that owned destroy call, and handler bookkeeping depth zero**. An arbitrary WM_NCDESTROY sender cannot create this receipt. Nested destroy callbacks use the pinned singleton; no worker can free/reuse the HWND or request storage. Callback depth zero means the handler has finished accessing mailbox state; pinned ABI epilogue instructions may still be returning. This is not a module-unload/callback-join or selected panel-close claim. Failed native destroy remains UnknownRetained, permanently revoked and resident; subsequent real owner service may retry it. The code does not manufacture an OS destroy-failure PASS.

Last-error values are preserved across public mailbox publication/read/ack/revoke/owner service and across the close-before-unhook work before calling the original unhook API. Existing hotkey Sender retirement and existing IO owner-zero/nonowner-2000ms Join remain in their prior contracts.

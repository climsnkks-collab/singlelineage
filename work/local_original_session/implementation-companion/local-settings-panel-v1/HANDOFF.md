## Minimal proposed LOCAL bridge contract — NOT IMPLEMENTED

This is a contract to implement and review, not a description of an existing endpoint. No opcode, named pipe name, listening port or invented original game message is assigned here.

1. **One selected binding.** Server registration captures the exact Broker writer/row and selected character lease plus current owned allied actor UID/generation and Host state/UI epoch. Native registration captures verified process instance, game HWND/UI thread and retained current WORLD identity. An opaque binding token maps those server objects inside the server; a Python pointer/object identity must never be sent as cross-process authority. Connection identity and selected/current checks remain server-side. Endpoint establishment must authenticate the exact owned process and existing local session rather than accepting a caller-supplied UID. This still needs an actual endpoint producer and receiver implementation.
2. **Model direction.** OPEN(binding, panel generation, revision, snapshot), RENDER(same panel, later revision, snapshot) and CLOSE(same panel) carry bounded typed data from `Host.view`. Enumerated commands and limits must be shared with server validation. The adapter retains the current server callback locally for each revision. Native UI receives no Python function or lease object. A server panel proxy can represent accepted pending open, but must expose pending/failed state and keep native-open confirmation separate; the existing Host's synchronous handle does not prove a visible window.
3. **Command direction.** A real user action produces COMMAND(binding, panel generation, displayed revision, command sequence, action, typed values). The server resolves the retained callback, checks selected state/current actor generation/UI epoch and invokes the original Host async command on its event loop. No receiver may call the Controller directly. Retired, unknown or stale revisions refuse; commands are not silently replayed across reconnect, and ambiguous delivery is not an excuse to auto-retry summon/dismiss. Server result and next model return with that sequence. The bridge itself does not issue game packets.
4. **Owner UI thread.** Only the established owner UI thread creates/renders/destroys panel controls. A transport receive worker may enqueue bounded immutable messages and revoke shared acceptance, but may not touch HWND controls or enter a server callback on the game's thread. An actual supported queue wake/owner dispatch implementation must be selected and reviewed; the existing natural GETMESSAGE observer alone does not guarantee prompt delivery. The panel must preserve original hook forwarding and must not call SetForegroundWindow/SetFocus, synthesize input, steal the cursor or activate on open. Owned HWND/no-activate display is a proposed implementation detail; keyboard editing/focus behavior remains a product decision rather than an invented workaround.
5. **Retirement and drain.** Selection change, WORLD change, server epoch invalidation, writer close and native Revoke immediately reject new commands. Revoke queues owner-thread close and detaches native control callbacks. Actual owner-thread destroy plus in-flight callback/command completion is the CLOSE acknowledgement. Keep code/storage and endpoint state alive until both directions drain. If the owner callback never runs or disconnect interrupts acknowledgement, record close UNKNOWN and retain pinned storage until process teardown; do not unload/reuse or report Closed. Preserve the inherited original Finish/forwarding behavior.
6. **Item/equipment boundary.** `open_items` consumes real server lease/actor/owner objects and needs the existing ITEM owner's admission contract. It cannot be serialized as a UID-only shortcut or point the selected player's inventory at the mage. That action remains unavailable until its genuine owner bridge is supplied; basic movement/support settings may be implemented independently.

# 싱글리니지 구현·검토 작업 규칙

2026-10-17 보안 작업 배정: 보안 전문 검토·구현이 필요한 항목은 아래 10절에 따라 **작업명에 ‘데이브레이크’를 넣은 Daybreak 세션**에 배정한다.

2026-10-17 사용자 확정 규칙: **이미 성공한 검사는 재사용하고, 변경된 부분과 직접 영향받는 경로만 검증한다.** 기존 전체 시나리오를 그대로 실행하지 않는다. 아래 과거의 기능·종료·재기동 묶음 규칙도 이 원칙에 따라 필요한 범위로 줄인다. 기존 Quit를 이용한 실행 정리는 계속하되, 성공한 Quit·왕복 이동·공격·60초 유지 등을 매번 재증명하지 않는다.

2026-10-16 시험 병합 규칙(2026-10-17 재사용 원칙 적용): 종료·재기동 등에 변경 영향이나 미확인이 있어 추가 검증이 필요한 경우에만 다음 기능 시험에 합친다. 기존 정상 종료 요청·필요한 복구는 같은 실행의 정리에 사용한다. 성공한 종료·재기동을 무조건 시험 순서에 붙이지 않으며, 종료 단독 게임 기동·반복 시험도 만들지 않는다. 일반 창 없는 검사 역시 변경 영향에 맞게 진행한다. 실제 게임은 사용자 포커스·커서·전역 입력을 건드리지 않는 백그라운드 경로를 사용한다.

적용일: 2026-10-15. 구현을 실제 실행 연결까지 진행하면서 필요한 독립검토를 유지한다.
이 문서는 앞으로의 운영 기준이며 과거 작업 시간이나 낭비 비율을 실측한 보고서가 아니다.
재개·중지는 최신 사용자 지시와 ACTIVE_TASK를 따른다. 이 규칙 작성 자체는 구현·실행의 재개 승인이 아니다.
제품 목표와 폐기·보존 경계는 [AGENTS.md](../AGENTS.md)와 [재조립 방향 검토](REASSEMBLY_STRATEGY_REVIEW_20261015.md)를 따른다.

## 1. 작업 단위와 시작

- 작업 단위는 원본의 실제 실행 경로와 그 경로에 필요한 의존성 묶음이다.
- 보통 1~2시간 또는 의미 있는 통합 한 단계로 묶는다. 함수 하나마다 새 검토 사이클을 만들지 않는다.
- 함수·객체 수에 맞춰 쪼개기보다 caller/callee, code/data, 초기화, 수명이 함께 닫히는 단위를 고른다.
- 시작 전에 기존 진행 노트에 목표, 현재 blocker, 바꿀 파일, 종료 증거를 합계 5줄 이하로 적는다.
- 이 기록을 위해 새 양식·보고서·승인 시스템을 만들지 않는다.
- 함수마다 별도 gate·nonce·receipt 파이프라인을 만드는 절차를 금지한다. 실제 실행 범위 식별·중복 실행 방지에 필요한 값은 공통 실행기에서 유지한다.
- 단일 선택 집합에서 실제 consumer로 연결할 경로를 정하고, 미확인 의존성을 명시한다.
- 다음 작업은 현재 기동·통합을 막는 연결, 확인된 원본 동작 차이, 그 둘을 해결하는 데 필요한 부품 순으로 고른다. 소비 경로가 정해지지 않은 부품 수 늘리기는 후순위다.
- ABI나 producer가 불명확하면 임의 stub로 통과시키지 않고 원문 보존 경계를 넓히거나 필요한 증거를 확보한다.

## 2. 위험별 검토 최소 기준

| 변경 위험 | 필요한 확인 | 독립검토 범위·횟수 |
|---|---|---|
| 문서, 경로 설명, 사람에게 보이는 출력만 변경하며 실행·기계 소비 계약은 불변 | 작성자가 정확성·형식을 검사 | 0회 |
| 기존 contract 안의 일반 구현 | 기존 자동검증과 main의 실제 diff 확인 | main 확인 1회; 작성 worker와 main이면 충분, 제3 worker 0명 |
| 새 ABI·object layout·allocator/EH/TLS, 초기화·간접 호출·수명 | 해당 위험의 계약·반례·실제 소비 연결 확인 | 해당 위험에 독립검토 1회 |
| 세이브 형식, 파괴적 작업, 프로세스 권한·격리 경계 | 데이터·권한·격리의 해당 경계 확인 | 해당 위험에 독립검토 1회 |

- 독립검토자는 해당 변경의 작성자가 아니며 그 위험을 판단할 역량이 있어야 한다.
- main이 작성자가 아니고 역량이 있으면 독립검토자 역할을 충족한다.
- 매번 main과 별도 reviewer가 같은 변경 전체를 중복 검토하지 않는다.
- main의 전문성이 부족하면 적합한 reviewer 1명으로 대체한다. 검토자를 추가 계층으로 쌓지 않는다.
- 이때 main은 실제 diff, 핵심 증거, 통합 결과를 확인하며 reviewer의 완료 선언만으로 완료 처리하지 않는다.
- 위험이 섞이면 그 위험이 생긴 부분에만 독립검토를 적용한다.
- ASM/COFF 파일이라는 이유로 검토 계층을 추가하지 않는다. 기존 변환 규칙·ABI·수명 계약을 재사용하는 조각은 자동검사와 변경분 확인으로 묶고, 새 계약·해석이 생긴 경계만 위험 검토한다.
- 검토 횟수는 해결되지 않은 결함을 무시할 허용량이 아니다. 아래 수정·순환 규칙으로 해결한다.

## 3. 결과 재사용과 재검증

- 이미 성공한 기능 검사는 재사용이 기본이다. 새 변경이 그 결과에 영향을 주는 구체적인 경로나 새로운 실패 근거가 있을 때만 해당 부분을 다시 검사한다. 다른 파일이나 같은 파일의 무관한 부분이 바뀌었다는 이유만으로 성공 결과 전체를 무효화하지 않는다.
- 실행 전에 변경 내용, 직접 영향받는 경로, 이번에 확인할 실패·성공 조건을 기존 진행 노트에 짧게 정한다. 기존 로그·결과를 해당 범위의 근거로 연결하고, 무관한 검사를 준비 단계나 선행조건으로 붙이지 않는다.
- 실제 게임 시험은 변경 지점에 도달하는 최소한의 기동·선택·상태 준비만 수행한다. 기존 공격·왕복 이동·60초 유지·전체 회귀는 변경 영향이 확인되지 않으면 생략한다. 새 기능에 필요한 준비 동작을 수행해도 그 기존 기능을 새로 검증한 성과로 세지 않는다.
- Quit는 같은 실행을 끝내는 기존 정리 경로로 사용한다. 성공한 정상 종료·같은 구성 재기동·저장 복원 검사의 반복은 관련 동작이 바뀌었거나 새 결함·미확인이 있을 때만 기능 시험에 합친다. 종료만을 위한 별도 기동이나 추가 대기는 금지한다.
- 입력, 도구·설정, 의존성, 검증 범위가 모두 같으면 기존 결과를 재사용한다.
- 새 결함, 실제 변경, 새 경계, 불완전한 자료가 있을 때만 관련 범위를 재검증한다.
- 재빌드는 변경의 영향을 받는 전이적 consumer까지 포함한다. 영향을 받지 않는 집합은 다시 빌드하지 않는다.
- 문서 metadata만 바뀌었다면 제품 code hash 갱신과 후속 검증을 연쇄 실행하지 않는다.
- 재사용 결과에는 기존 근거 위치와 적용 범위를 남기며 새 실행 결과처럼 표시하지 않는다.
- 현재 runtime 상태, PID·실행 이미지·소유권·권한은 실제 작업 경계에서 새로 확인한다.
- 이전 receipt나 PID 기록은 현재 프로세스 신원·권한 확인을 대신할 수 없다.
- 확인 실패는 UNKNOWN으로 유지한다. 메모리 상태를 화면 표시나 게임 완료로 확대하지 않는다.

## 4. 지적과 수정의 종료

- blocker에는 재현 위치, 영향, 해당 원본 또는 계약, 필요한 검사를 함께 적는다.
- 취향·스타일·범위 밖 개선만 후속으로 분리한다. 완료 주장에 영향을 주는 원본 동작 차이는 차단한다.
- 작성자가 수정한 뒤 reviewer는 수정 diff와 해당 반례만 확인한다. 전체 검토를 처음부터 반복하지 않는다.
- 같은 지적 해결에 2회 실패하거나 독립검토가 2회 순환하면 원인·설계·작업 단위를 바꾼다.
- 한 명에게 해결을 맡기고 필요한 검증만 닫는다. reviewer 수를 늘려 순환을 연장하지 않는다.
- 검토기를 검토하기 위한 새 검토기를 만들지 않는다.
- 모르는 경계는 명시하고 해당 안전하지 않은 호출만 막는다. 독립적인 다른 경로는 계속 진행한다.
- 도구 실패와 제품 결함을 구분한다. 검증 도구의 미해결 결과는 UNKNOWN이며 제품 버그로 단정하지 않는다.

## 5. 완료와 다음 단계

- 실행 경로를 완료로 닫으려면 필수 표적 검사 통과와 실제 consumer 통합 증거가 모두 필요하다.
- 심각도 이름과 무관하게 해당 완료 주장에 영향을 주는 기능·원본 동작·연결·수명·데이터·안전 결함은 0건이어야 한다.
- 필수 검사는 변경된 동작·위험·기존 계약에 대응하는 검사로 정한다.
- 자료만 준비했다면 결과를 **자료 준비**로 표시하고 실행 경로 완료로 표시하지 않는다.
- 자료조사 묶음은 정한 질문에 답하고 근거·남은 미확인을 기록하면 종료할 수 있다. 그 묶음을 끝내기 위해 범위 밖 의존성 조사나 검토를 계속 늘리지 않는다.
- 상태는 **원문 확인 / 연결 확인 / 동작 확인**으로 나누고 각 근거와 미확인을 적는다.
- 원문 일치·컴파일·자체 테스트 통과가 연결 또는 원본 동작 동등성을 대신하지 않는다.
- 종료 조건을 만족하면 즉시 다음 단계로 이동한다. 추가 안심 검증을 붙이지 않는다.
- 전체 제품 완료는 독립 기동과 원본 전체 동작 재현 기준을 유지한다. 작업 묶음 완료와 구분한다.

## 6. 시간 배분과 경보

- 작업 묶음별 목표는 실질 구현·필요한 원본 조사 70% 이상, 검토 관련 합계 30% 이하이다.
- 구현에는 필요한 원본 조사·원본 코드 변경·실제 제품 연결만 포함한다. 순수 gate·검사기·문서 작업은 제외한다.
- 검토 관련 합계에는 컴파일·테스트·독립검토·재핀, 검토 도구 작업, 기록·조율을 모두 포함한다.
- 이 비율은 새로운 운영 경보 기준이다. 기존 작업의 실제 소요 비율이라고 주장하지 않는다.
- 작은 문서 작업에는 비율을 집계하지 않는다.
- 추산은 기존 진행 노트 한 줄로 남긴다. 새 telemetry나 시간 측정 도구를 만들지 않는다.
- agent가 실제 작업한 시간을 대략 추산하며 외부 응답·빌드 대기는 별도로 적는다. 정밀 타이머는 만들지 않는다.
- 검토 작업을 구현으로 이름 바꾸어 비율을 맞추지 않는다.
- 시간 목표 때문에 미검증 결과를 PASS로 바꾸거나 필수 검사를 생략하지 않는다.
- 필수 고위험 검사가 더 필요하면 정확한 blocker와 필요한 검사를 적어 예외로 계속하고 다른 작업도 진행한다.
- 한 묶음에서 초과하면 같은 변경의 중복 검증·추가 하네스 작업을 중지하고 필요한 검증만 마친다.
- 다음 묶음은 의존성·통합 단위를 다시 설계해 실제 실행 연결에 더 직접적으로 기여하도록 한다.
- 두 묶음 연속 초과하면 새 검토 파이프라인 생성을 멈추고 중복 검사를 제거한 뒤 기존 도구로 단일 실행 경로의 연결을 우선한다. 이를 이유로 별도 검증기 통합 프로젝트를 시작하지 않는다.

## 7. 검증 도구의 범위

- 새 검증 도구는 기존 도구로 검출하지 못하는 구체적 실패, 실제 사용처, 종료 조건이 있을 때만 허용한다.
- 그 실패를 확인하는 가장 작은 도구로 만들고 기존 공통 실행기·검증기·manifest를 먼저 활용한다.
- 같은 묶음에 무관한 도구 리팩터링을 넣지 않는다.
- 도구를 늘린 수, seal·receipt 수는 제품 진척으로 집계하지 않는다.
- 검증기 오류 수정은 해당 수정 범위와 반례만 다시 검사한다.
- 새 도구 수리가 2번 반복되면 기존 도구 대안이나 작업 단위 변경으로 전환한다. UNKNOWN을 숨겨 PASS로 만들지 않는다.

## 8. 기록과 진행지표

- 기본 산출물은 코드 diff, 기존 원문 참조, 필요한 검증 결과 1건, 미해결 항목이다.
- 검증 결과 1건은 필요한 검사들의 요약이며 필수 검사 수를 1개로 제한한다는 뜻이 아니다.
- 원기록은 보존하되 매회 복제하거나 author→main→peer→root→final seal 사슬을 만들지 않는다.
- AGENTS와 ACTIVE_TASK에는 짧은 최신 상태·근거·다음 작업만 유지하고 거대한 이력을 반복 붙이지 않는다.
- 이번 규칙 적용을 이유로 기존 기록을 이동하거나 삭제하지 않는다.
- 진척은 실제 경로의 blocker 해결, 링크·실행 연결, 관찰된 원본 동등성으로 판단한다.
- 객체·테스트·hash 개수만으로 제품 진척이나 전체 완료율을 표시하지 않는다.

## 9. 보존·권한·기존 절차

- 실제 permissions, 원본·자원·사용자 저장 데이터 보존, 프로세스 신원·격리, 사용자 중지 지시는 계속 지킨다.
- 폐기한 자체 앱의 호스트·UI·Runtime/Controller·별도 싱글 규칙을 다시 제품 기반으로 사용하지 않는다.
- 기존 기록의 artifact별 다중검토 절차는 새 작업에 자동 승계하지 않는다.
- 이미 발행된 실행권한 범위나 명시적 승인 경계를 이 규칙으로 조용히 완화하지 않는다.
- 기존에 승인된 범위에는 사용자 재승인을 기본 gate로 추가하지 않는다.
- 일반 권한과 창 없는 작업을 우선하며 실패·취소한 UAC를 자동 반복하지 않는다.

## 10. 보안 전문 세션 배정

- 사이버 보안 관련 거부·제한을 만나면 사유, 대상, 접근 권한, 기존 근거를 정리해 Daybreak 세션의 보안 전문 검토에 배정한다. 해당 세션은 이 자료를 바탕으로 수행 가능한 범위와 해결 방법을 판단한다.
- 작업명에는 반드시 **데이브레이크**를 넣는다. 예: `싱글리니지 데이브레이크 — 보안 검토 항목명`. 해당 목적의 세션 생성·작업 전달은 이번 사용자 지시로 승인된 범위다.
- 모델은 세션 도구가 제공하는 Daybreak 모델을 명시하고 실제 선택을 확인한다. 현재 도구의 모델 ID는 `gpt-daybreak-blue-latest`다. 일반 `gpt-6-sol`로 임의 대체하지 않으며 메인·일반 구현 워커의 기존 설정은 유지한다.
- 전달할 작업에는 구체적인 질문, 대상·권한·수행 범위, 거부·제한의 원문 사유, 소유 파일, 필요한 산출물을 포함한다. 기존 구현·REA 채팅의 파일 및 실행 소유권을 함께 넘기지 않는다.

# 싱글리니지 지속 개발 작업 규칙

통합일: 2026-10-17 KST
적용 대상: Codex 통합 담당, 구현 담당, REA 분석 담당과 각 작업자

원본 기반 클라이언트와 자체 로컬 서버를 연결해 사용자가 합의한 실제 플레이 기능을 완성한다. 사용자 동작 하나에 필요한 연결을 작업 단위로 삼고, 확인된 근거를 재사용하며, 실패 지점에 맞는 다음 행동을 선택한다.

이 문서는 기존 구현·검토 규칙과 사용자 제공 `SINGLELINEAGE_WORK_RULES.md`를 통합한 상시 운영 기준이다. 현재 기능, 함수 주소, 실행 번호, 후보 해시, 담당 세션, 모델 설정, 일시 중지 상태는 [현재 상태와 작업 계획](ACTIVE_TASK.md)에서 관리한다. 사용자의 최신 명시적 지시와 실제 권한 범위를 따르며, 이미 승인된 작업에 재승인을 기본 절차로 추가하지 않는다. 이 문서 자체로 구현·실행의 재개 권한이나 완료 사실을 만들지 않는다.

## 1. 제품 목표와 구현 노선을 유지한다

- 주력은 원본 기반 클라이언트와 자체 로컬 서버다. 사용자가 방향을 바꾸지 않는 한 전면 클라이언트 재작성이나 별도 모사 앱으로 전환하지 않는다.
- 제품 목표와 폐기·보존 경계는 [AGENTS.md](../AGENTS.md)와 [재조립 방향 검토](REASSEMBLY_STRATEGY_REVIEW_20261015.md)를 따른다.
- 원래 화면·입력·동작을 보존하고 공식 런처나 공식 서버의 선행 실행 없이 사용할 수 있는 제품을 목표로 한다.
- 클라이언트와 맞아야 하는 메시지 구조·식별자·상태 전이·응답 순서를 확인한다. 서버의 수치·규칙은 합의한 로컬 정책과 원본 근거를 구분한다.
- 클라이언트만으로 확인되지 않는 서버 계산식을 추측해 원본 규칙으로 확정하지 않는다.
- 작업 단위의 완료와 사용자가 합의한 전체 제품의 완료를 구분한다.

## 2. 현재 상태를 읽는 진입점은 하나로 유지한다

- 기존 현재 상태 문서에 현재 목표, 확인된 결과와 근거, 막힌 지점, 담당자, 다음 행동을 짧게 유지한다.
- 새 작업은 현재 상태와 해당 기능의 근거부터 읽는다. 전체 이력과 전체 분석 결과를 매번 다시 읽지 않는다.
- 과거 기록은 보존하고 근거로 연결한다. 과거의 ‘최신’, 중지·재개, 다음 작업 지시가 현재 지시로 읽히지 않도록 당시 기록임을 표시한다.
- 현재 상태 문서는 실제 사용자 지시와 확인된 결과를 반영한다. 문서의 표현만으로 실행 권한이나 완료 사실을 만들어내지 않는다.
- 새 관리 시스템, 중복 상태 문서, 별도 승인 양식은 만들지 않는다.
- 기본 산출물은 코드 diff, 기존 원문 참조, 필요한 검증 결과 요약, 미해결 항목이다. 결과 요약을 한 건으로 묶는 것은 필수 검사 수를 한 개로 제한한다는 뜻이 아니다.

## 3. REA 조사와 구현을 사용자 동작 하나로 묶는다

- 한 작업은 사용자 입력, 원본 처리, 서버 요청·응답, 클라이언트 반영 중 현재 완성하려는 동작과 필수 의존성으로 정한다.
- 다음 작업은 현재 기동·통합을 막는 연결, 확인된 원본 동작 차이, 그 둘에 필요한 부품 순으로 고른다. 소비 경로가 정해지지 않은 부품 수 늘리기는 후순위다.
- ABI나 데이터 생산자가 불명확하면 임의 stub로 통과시키지 않고 원문 보존 경계를 넓히거나 필요한 근거를 확보한다.
- 함수 하나를 분석할 때마다 별도의 구현·실행·검토 사이클을 만들지 않는다.
- 시작 시 이미 확인된 연결과 남은 질문을 구분한다. 필요한 호출 관계, 데이터 생성·소비, 초기화, 객체 소유·수명을 함께 조사한다.
- 조사 중 다음에 반드시 필요한 의존성이 드러나면 같은 묶음에서 이어간다. 그 의존성이 빠진 상태로 실행해 다시 막히는 일을 줄인다.
- 조사 범위는 현재 동작의 필수 연결에 한정한다. 무관한 기능, 전체 호출 그래프, 전체 프로토콜 복원을 선행 조건으로 추가하지 않는다.
- 실행 상태가 있어야 답할 수 있는 지점에 도달하면 정적 조사를 끝없이 늘리지 않는다. 필요한 관측과 판정 조건을 남기고 기존 실행 관측으로 연결한다.
- 조사 담당은 정한 질문의 답, 근거, 남은 미확인, 구현에 필요한 조건을 전달하면 해당 조사 묶음을 마친다. 조사 종료를 위해 모든 주변 의존성을 해석하지 않는다.

## 4. REA 세션과 분석 결과를 재사용한다

- 구현 채팅에서는 REA 분석을 실행하지 않고 기존 별도 REA 분석 채팅에 현재 동작을 막는 질문을 전달한다. 기존 파일·실행 소유권과 모델 합의는 유지한다.
- 같은 대상을 계속 조사할 때는 지원되는 범위에서 같은 MCP 연결과 활성 분석 세션을 사용한다. 분석 주제만 달라졌다는 이유로 매번 닫고 다시 열지 않는다.
- 새 분석 전에 기존 Evidence의 요약·함수 식별 정보·필요한 부분을 먼저 조회한다. 저장된 결과를 읽기 위해 동일 분석을 반복하지 않는다.
- 분석 결과에는 대상 바이너리 식별값, 분석 도구·설정, 함수 위치, 원문 근거와 미확인을 함께 보존한다.
- 설치된 REA가 지원하면 Evidence 내보내기와 snapshot을 사용한다. snapshot은 일치하는 기존 질의 결과의 재사용 수단이며 새로운 질문이나 현재 실행 상태의 증거를 대신하지 않는다.
- 시간초과가 나면 도구 기동, 대상 초기 분석, 개별 질의, 클라이언트 대기 시간, 정리 실패를 구분한다. 동일 명령의 무조건 재시작으로 처리하지 않는다.
- 분석기 실행이 계속되고 있는지와 해당 오류의 복구 조건을 확인한 뒤 필요한 복구만 수행한다.
- 도구 이름과 옵션은 실제 설치 버전의 지원 여부를 확인한다. 이 규칙을 적용하기 위해 분석 환경을 전면 교체하지 않는다.

## 5. 병렬 작업과 실제 실행의 소유권을 분명히 한다

| 역할 | 책임 |
|---|---|
| 통합 담당 | 현재 우선순위, 공용 연결과 실행 구성, REA 요청 순서, 실제 제품 통합·설치·게임 실행·정리, 결과 수용 |
| 클라이언트 구현 담당 | 배정된 원본 호출·UI·객체 연결, 필요한 빌드와 표적 검사 |
| 서버 구현 담당 | 배정된 요청 처리·상태 변화·응답·저장 연결과 필요한 검사 |
| REA 담당 | 현재 동작의 미확인 원본 계약 조사, 기존 근거 재사용, 답변·미확인·다음 관측 전달 |

- 기존에 정한 담당자와 파일 소유권을 따르며 같은 파일을 동시에 수정하지 않는다. 소유 범위를 바꿀 때는 통합 담당과 명시적으로 조정한다.
- REA 결과에 의존하지 않는 구현·로그 분석·검사는 병렬로 진행한다. 확인되지 않은 원본 조건을 추측해 선행 구현하지 않는다.
- 같은 분석을 여러 담당자가 중복 수행하도록 인원만 늘리지 않는다.
- 실제 게임 검증은 통합 담당이 승인된 기존 백그라운드 실행 경로로 계속한다. 사용자 포커스·커서·전역 입력에 간섭하지 않는다. 실행기 옵션이나 focus API 호출이 없다는 사실만으로 백그라운드 격리를 보장했다고 판단하지 않는다.
- 원본·사용자 저장·프로세스 격리와 기존 실행 범위를 보존한다. 현재 역할·모델·전문 검토 배정은 기존 합의와 실제 제공 도구를 따른다.

## 6. 실행 전 질문을 정하고 실패 지점에 따라 다음 작업을 고른다

실행 전 기존 진행 노트에 이번 변경, 확인할 결과, 결과를 가르는 관측을 짧게 적는다. 진단 목적의 실행이라면 어떤 원인 후보를 구별하는지 명시한다.

| 관측된 실패 지점 | 우선 확인 | 다음 행동 |
|---|---|---|
| 분석 도구나 시험 준비 단계 | 도구 기동·세션·설정·대기·정리 상태 | 해당 도구나 준비 경로를 복구한다. 게임 기능 결함으로 확대하지 않는다. |
| 원본 호출 전에 거부 | 현재 객체·등록·소유·호출 시점과 어댑터의 전제조건 | 기존 실행 관측과 연결 코드를 확인한다. 구조가 불명확한 부분만 REA에 요청한다. |
| 원본 callback 반환 후 요청 미발생 | 선택 대상과 요청 생성 조건, 실제 실행 시점 | 해당 조건과 관측을 대조한다. 반환만으로 요청 성공을 선언하지 않는다. |
| 서버 요청 수신 후 처리 실패 | 파싱·handler·상태 변경·응답·저장 | 해당 서버 구현과 표적 검사를 수정한다. |
| 응답 전달 후 클라이언트 반영 실패 | 응답 필드·소비 함수·상태 갱신·표시 경로 | 필요한 소비 경로와 실행 관측을 확인한다. |
| 관측만으로 분류 불가 | 어떤 사실이 빠졌는지 | 미확인으로 남기고 가설을 구별할 최소 관측을 보완한다. |

- 원래 사용자 동작의 필수 조건과 별도 시험용 호출 어댑터가 요구하는 조건을 구분한다.
- 원본이 이미 관리하는 호출·초기화·소유 경로를 활용할 수 있는지 먼저 확인한다.
- 새로운 가설·변경·관측 없이 같은 실행을 반복하지 않는다.
- blocker에는 재현 위치, 영향, 해당 원본·계약, 필요한 검사를 적는다.
- 같은 원인·지적 해결에 두 차례 실패하거나 독립검토가 두 차례 순환하면 담당자·원인·가설·호출 경계·작업 단위를 정리하고 접근을 바꾼다. 검토자 수를 늘려 순환을 연장하지 않는다. 이 기준은 같은 실행을 두 번 허용한다는 뜻이 아니다.
- 미확인이 필요한 호출과 완료 주장에 미치는 범위를 명시한다. 해당 안전하지 않은 호출만 막으며 독립적으로 진행 가능한 작업은 계속한다.
- 도구의 미해결 결과는 UNKNOWN이다. 도구 실패를 제품 버그로 단정하거나 UNKNOWN을 숨겨 PASS로 만들지 않는다.

## 7. 확인된 사실을 재사용하고 현재 실행 상태는 필요한 경계에서 확인한다

- **이미 성공한 검사는 재사용하고 변경된 부분과 직접 영향받는 경로만 검증한다.** 버전, 입력, 도구·설정, 의존성, 조건·검증 범위가 같으면 기존 코드 계약과 성공 결과를 재사용한다.
- 새로운 변경, 직접 영향 경로, 새 결함·경계, 불완전한 근거가 있을 때만 관련 부분을 다시 조사하거나 검사한다. 다른 파일이나 같은 파일의 무관한 부분이 바뀌었다는 이유로 성공 결과 전체를 무효화하지 않는다.
- 현재 프로세스 신원, 실행 이미지, 객체 소유·등록·유효 상태처럼 실행마다 달라지는 사실은 필요한 작업 경계에서 새로 확인한다.
- 이전 실행의 PID, 포인터, receipt, 객체 상태를 현재 실행의 증거로 사용하지 않는다.
- 정적 코드·분석 메모리의 사실과 실제 프로세스에서 관측한 사실을 구분한다. 확인 실패는 UNKNOWN으로 유지하고 메모리 상태를 실제 화면 표시나 게임 완료로 확대하지 않는다.
- 채택된 REA 근거 파일은 고정하고 후속 설명은 진행 기록에 남긴다. 근거 계약이 바뀔 때만 새 버전과 영향받는 소비 코드를 함께 갱신한다.
- 기계가 소비하지 않는 설명의 변경으로 제품 전체를 다시 검증하거나 제품 code hash 갱신을 연쇄 실행하지 않는다. 전체 hash를 검사하는 근거 문서는 기계 소비 계약의 일부이므로 실제 변경 영향을 확인한다.
- 재사용한 결과는 원래 근거 위치와 적용 범위를 표시하며 새 실행 결과로 집계하지 않는다.

## 8. 변경 범위에 맞춰 최소한으로 검증하고 필요한 정리는 수행한다

- 실제 게임에서는 변경 지점에 도달하는 최소한의 기동·선택·상태 준비와 해당 기능만 확인한다. 기존 기능별 축소 실행 모드를 우선 활용한다. 준비 동작을 수행해도 기존 기능을 새로 검증한 성과로 세지 않는다.
- 성공한 공격·왕복 이동·장시간 유지·정상 종료·재기동·저장 복원을 매번 시험 순서에 붙이지 않는다.
- 해당 기능 자체의 요구나 변경 영향에 필요한 경우에만 응답·효과·저장·재기동을 검증 범위에 포함한다. ‘동작 하나의 연결’이 매번 전체 시나리오를 뜻하지 않는다.
- 게임이 살아 있는 실행에서는 기존 Quit로 종료를 요청하고 결과 관측·필요한 복구·자원 정리를 수행한다. 정리 수행과 종료 기능의 반복 재검증을 구분한다. 정상 종료 실패·미확인·강제 정리는 실제 결과대로 기록한다.
- 종료·재기동 추가 검증이 필요한 경우 다음 기능 시험에 합친다. 종료만을 위한 별도 게임 기동·반복 시험·추가 대기를 만들지 않으며 정상 Quit 미해결을 독립적인 다음 기능 전체의 중지 조건으로 두지 않는다.
- 빌드와 단위·통합 검사는 변경의 영향을 받는 전이적 소비 경로까지 포함하되 무관한 집합은 재실행하지 않는다.
- 테스트 실행 진입점과 명령을 일관되게 사용해 호출 방식에 따른 수집 범위 차이를 없앤다.
- 실제 프로세스가 있어야 확인할 조건은 실제 환경에서 검증한다. mock이나 정적 검사 통과로 실행 증거를 대신하지 않는다.

## 9. 검토와 도구 작업을 구체적인 위험에 비례시킨다

| 변경 위험 | 필요한 확인 | 독립검토 범위·횟수 |
|---|---|---|
| 문서, 경로 설명, 사람에게 보이는 출력만 변경하며 실행·기계 소비 계약은 불변 | 작성자가 정확성·형식을 검사 | 0회 |
| 기존 contract 안의 일반 구현 | 기존 자동검증과 main의 실제 diff 확인 | main 확인 1회; 작성 worker와 main이면 충분, 제3 worker 0명 |
| 새 ABI·object layout·allocator/EH/TLS, 초기화·간접 호출·수명 | 해당 위험의 계약·반례·실제 소비 연결 확인 | 해당 위험에 독립검토 1회 |
| 세이브 형식, 파괴적 작업, 프로세스 권한·격리 경계 | 데이터·권한·격리의 해당 경계 확인 | 해당 위험에 독립검토 1회 |

- 독립검토자는 해당 변경의 비작성자이며 그 위험을 판단할 역량이 있어야 한다.
- 통합 담당자가 비작성자이며 해당 위험을 판단할 수 있으면 독립검토자 역할을 겸할 수 있다. 동일 변경 전체에 검토 계층을 추가하지 않는다.
- 통합 담당자의 전문성이 부족하면 적합한 검토자 한 명으로 대체한다. 검토자를 추가 계층으로 쌓지 않는다.
- 전문 검토자를 쓴 경우 통합 담당자는 실제 diff·핵심 증거·통합 결과를 확인한다. 완료 선언만으로 수용하지 않는다. 위험이 섞이면 그 위험이 생긴 부분에만 독립검토를 적용한다.
- ASM/COFF 파일이라는 이유로 검토 계층을 추가하지 않는다. 기존 변환 규칙·ABI·수명 계약을 재사용하는 조각은 자동검사와 변경분 확인으로 묶고 새 계약·해석이 생긴 경계만 위험 검토한다.
- 취향·스타일·범위 밖 개선은 후속으로 분리하고 완료 주장에 영향을 주는 원본 동작 차이는 해결한다.
- 지적 수정 후에는 수정분과 해당 반례만 다시 확인한다. 검토 횟수는 미해결 결함을 무시하는 통과 기준이 아니다.
- 새 도구는 기존 도구로 확인하지 못하는 구체적 실패, 실제 사용처, 종료 조건이 있을 때만 최소 범위로 만든다. 기존 공통 실행기·검증기·manifest를 먼저 활용한다.
- 함수별 gate·nonce·receipt·검토 파이프라인, 검토기의 검토기, author→main→peer→root→final 승인 사슬, 무관한 도구 리팩터링을 만들지 않는다. 실제 실행 식별·중복 방지에 필요한 값은 공통 실행기에서 유지한다.
- 검증 도구 수정은 수정분과 반례만 다시 검사한다. 새 도구 수리가 두 차례 반복되면 기존 도구 대안이나 작업 단위 변경으로 전환한다.
- 작업 묶음의 실질 구현·필요 원본 조사 70% 이상, 검토·검증·도구·기록·조율 합계 30% 이하를 보조 경보로 사용한다. 검토 작업을 구현으로 이름 바꾸어 맞추지 않으며 작은 문서 작업에는 집계하지 않는다.
- 추산은 기존 진행 노트 한 줄로 남기고 외부 응답·빌드 대기는 구분한다. 과거 작업의 실측 비율로 주장하거나 정밀 계측·보고 절차를 새로 만들지 않는다.
- 초과하면 중복 검사·새 하네스를 줄이고 다음 작업 단위를 조정한다. 두 묶음 연속 초과하면 새 검토 파이프라인 생성을 멈추고 기존 도구로 실제 소비 연결을 우선한다. 별도 검증기 통합 프로젝트로 확장하지 않는다.
- 시간 목표 때문에 필수 검사·알려진 결함을 생략하거나 미검증 결과를 PASS로 바꾸지 않는다. 필요한 고위험 검사는 blocker와 범위를 적어 계속하고 독립 작업도 진행한다.
- 실제 접근 제한과 검토 거부의 사유를 보존한다. 제한을 없애기 위한 우회 재시도로 취급하지 않으며 가능한 독립 작업을 계속한다.

### 보존·권한·기존 절차

- 실제 permissions, 원본·자원·사용자 저장 데이터 보존, 프로세스 신원·격리, 사용자 중지 지시는 계속 지킨다.
- 폐기한 자체 앱의 호스트·UI·Runtime/Controller·별도 싱글 규칙을 다시 제품 기반으로 사용하지 않는다.
- 기존 기록의 artifact별 다중검토 절차는 새 작업에 자동 승계하지 않는다.
- 이미 발행된 실행권한 범위나 명시적 승인 경계를 이 규칙으로 조용히 완화하지 않는다.
- 기존에 승인된 범위에는 사용자 재승인을 기본 gate로 추가하지 않는다.
- 일반 권한과 창 없는 작업을 우선하며 실패·취소한 UAC를 자동 반복하지 않는다.

## 10. 보안 전문 세션 배정

- 보안 전문 검토·구현이 필요한 항목은 Daybreak 세션에 배정한다. 사이버 보안 관련 거부·제한을 만나면 사유, 대상, 접근 권한, 기존 근거를 전달해 수행 가능한 범위와 해결 방법을 판단하게 한다.
- 작업명에는 반드시 **데이브레이크**를 넣는다. 예: `싱글리니지 데이브레이크 — 보안 검토 항목명`. 해당 목적의 세션 생성·작업 전달은 기존 사용자 지시로 승인된 범위다.
- 모델은 세션 도구가 제공하는 Daybreak 모델을 명시하고 실제 선택을 확인한다. 현재 도구의 모델 ID는 `gpt-daybreak-blue-latest`다. 일반 `gpt-6-sol`로 임의 대체하지 않으며 메인·일반 구현 워커의 기존 설정은 유지한다.
- 전달할 작업에는 구체적인 질문, 대상·권한·수행 범위, 거부·제한의 원문 사유, 소유 파일, 필요한 산출물을 포함한다. 기존 구현·REA 채팅의 파일 및 실행 소유권을 함께 넘기지 않는다.

## 11. 실제 기능 증거로 완료를 판단하고 다음 승인된 작업을 이어간다

| 상태 | 필요한 근거 |
|---|---|
| 원문 확인 | 해당 버전의 코드·형식·조건이 근거로 확인됨 |
| 연결 확인 | 해당 코드가 실제 제품의 생산자·소비 경로에 연결됨 |
| 동작 확인 | 정한 조건에서 실제 입력·요청·상태 변화 등 해당 기능의 결과가 관측됨 |
| 미확인 | 필요한 근거가 아직 없거나 관측 결과만으로 판단할 수 없음 |

- 컴파일 성공, 원문 일치, callback 반환, 요청 수신, 저장, 화면 반영은 각각 입증한 범위로 기록한다.
- 기능 완료에는 정한 동작 결과, 실제 소비 연결, 해당 변경에 필요한 표적 검사와 결함 해결 근거가 있어야 한다. 심각도 이름과 무관하게 완료 주장에 영향을 주는 기능·원본 동작·연결·수명·데이터·안전 결함은 해결돼야 한다.
- 진척은 실제 경로의 막힘 해결, 링크·실행 연결, 관찰된 원본 동등성으로 판단한다. 코드·함수·파일·객체·테스트·hash·seal·receipt 개수를 제품 완료율로 환산하지 않는다.
- 자료만 준비했으면 **자료 준비**로 표시하고 조사 종료와 기능 완료를 구분한다. 원문 일치·컴파일·자체 테스트는 연결이나 원본 동작 동등성을 대신하지 않는다. 전체 제품 완료는 독립 기동·원본 전체 동작 재현이라는 합의 목표로 판단한다.
- 정한 완료 조건을 만족하면 추가 안심 검증 없이 해당 단위를 마치고 다음 승인된 작업을 이어간다. 중간 단위 완료를 이유로 매번 사용자에게 계속할지 묻지 않는다.
- 사용자 중지나 실제 권한·자료 부족으로 진행할 수 없는 경계에서는 막힌 행동과 필요한 조치를 구체적으로 알린다. 영향을 받지 않는 작업은 가능한 범위에서 진행한다.
- 결과는 변경 내용, 확인된 동작과 근거, 남은 미확인, 다음 행동으로 짧게 보고한다.

## 작업마다 사용할 기록

기존 현재 상태 문서에 아래 다섯 항목을 시작·마감 시 짧게 갱신한다. 별도 양식 파일은 만들지 않는다.

```text
목표: 이번에 완성하거나 확인할 사용자 동작
기존 근거: 재사용할 분석·구현·성공 결과와 적용 범위
막힌 연결: 남은 질문과 이번 관측이 구별할 조건
변경·검증: 담당 파일·범위, 변경 지점, 직접 영향받는 검사, 필요한 실행 정리
결과·다음: 확인된 단계, 근거, 남은 미확인, 바로 이어갈 작업
```

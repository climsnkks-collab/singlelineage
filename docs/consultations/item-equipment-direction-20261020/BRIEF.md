# ITEM-EQUIPMENT 구현 방향 검토 요청

이 요청의 목적은 기능 전체의 구현 노선·설계 선택·우선순위·검증 전략을 점검하는 것입니다. 특정 함수나 메모리 읽기 하나의 진단은 목적이 아닙니다. 아래 요약은 공개 가능한 범위이며 원본 바이너리·자원·저장·실행 로그·역분석 원문·객체 레이아웃·비밀정보는 포함하지 않습니다.

## 전체 목표와 현재 노선

원본 데스크톱 게임 클라이언트와 자원을 보존하고, 공식 로그인/서버에 의존하지 않는 로컬 서버를 연결해 원래 사용자 동작을 재현하려 합니다. 현재 기능은 인벤토리·아이템 사용·장비·버리기/줍기·저장 복원입니다. 한 기능의 완료는 입력 → 원래 UI 처리 → 실제 요청 → 로컬 서버 상태/내구 저장 → 응답 → 원래 클라이언트 소비 → 다음 동작·재선택·종료까지입니다. 원본 클라이언트의 모든 함수를 소스화하는 것은 선행조건이 아닙니다.

현재 승인된 제품 노선은 원본 기반 클라이언트 + 로컬 서버입니다. 별도 모사 UI나 전면 클라이언트 재작성은 현재 구현안이 아닙니다. 확인하지 못한 공식 서버 수치·규칙은 동등하다고 주장하지 않고 명시된 로컬 정책과 구분합니다.

클라이언트 bridge는 보유된 실제 객체·원래 등록/선택·정상 실행 frame 아래 원래 callable/body를 호출합니다. 전역 입력이나 사용자 포커스를 건드리지 않습니다. 실제 게임 검증은 별도 통합 소유자가 격리된 비입력 desktop과 소유 process/job으로 실행·정리합니다. 원본·사용자 저장은 보존하며 시험 저장은 사본입니다.

로컬 서버는 하나의 실제 source-module/Store/provider graph와 명시된 policy를 사용합니다. 선택·row/task·revision·내구 CAS·송신/drain·수명 상태를 결속합니다. 기능별 guard를 임시 해제하거나 임의 상태/응답을 주입해 통과시키지 않습니다. 실패와 미확인은 실제 결과대로 남깁니다.

## 확인된 사실과 반복 패턴

- 버리기 원 입력/선택 경로와 원 Drop body의 정상 반환은 실제 클라이언트 시험에서 확인됐습니다. 정상 종료와 저장 보존도 별도 확인됐습니다. 이 사실을 수량 팝업·서버 버리기·다시 줍기 성공으로 확대하지 않습니다.
- 수량 팝업의 초기 acquire 단계에서 같은 Helper 범주 거부가 반복됐습니다. 원 계약상 선택적 cancel 역할의 null 허용을 보존한 수정 후에도 같은 범주였습니다. 최신 출력 전용 진단으로 초기 callback dispatch pointer가 null인 최초 조건을 좁혔습니다. 이는 원인이 생산자 누락·시점·다른 분기·퇴역 중 무엇인지를 확정하지 않습니다.
- 기존 원문 대조상 Drop의 정보 container 경로는 UI pair가 있을 때 같은 호출 stack에서 원 dispatcher와 설치 경로를 동기 호출합니다. 따라서 '나중 dispatcher를 직접 한 번 더 호출하면 된다'거나 '그냥 대기하면 된다'는 결론은 근거가 없습니다. 별도 원본 조사 담당이 실제 생산·분기·등록·소거·정상 반환 계약을 확인 중입니다.
- source/build·정적 guard·개별 원 body 반환이 맞아도 실제 다음 소비가 연결됐는지는 따로 확인해야 했습니다. 작은 guard 수정과 재기동을 반복하는 방식은 기능 목표의 진전과 다른 방향으로 흐를 위험이 있습니다.
- 독립된 동일 기능의 backend 묶음에서는 실제 Factory → 거래/현재 인벤토리 채택 → 원 Use 수신 → 실제 장비 효과 → 기존 sidecar 저장/복원·응답·정리를 코드 fixture로 확인했습니다. 실제 장비 UI/능력치·공식 규칙 동등성은 아직 확인하지 않았습니다.
- 그 직후 실제 다음 NPC/자원 consumer가 남은 ACCEPTED Use intent 때문에 거부되는 cross-feature 수명 결손을 찾았습니다. 원 Native 결과 소비자가 모든 결과를 확인한 뒤 intent를 소비하는 callee가 없었습니다. 현재 같은 issued intent/ordinal/선택/source·실 Native 결과 parser·실 장비 DRAINED operation을 최종 소비한 뒤에만 원 cleanup을 잇는 전용 경로를 구현·직접 검증 중입니다. 일반 current guard를 완화하지 않습니다. Native 결과 없음·불확실·취소·기한 만료는 정상 완료로 바꾸지 않습니다.

## 유지할 가정과 반증할 가정

유지: 원래 UI/요청/객체 수명과 실제 소비를 보존하며, 생성·호출·서버·저장·응답·정리를 기능 단위로 연결합니다. 메모리 상태를 강제하거나 callback/capture/거래/ACK를 가짜로 만들지 않습니다. 원 body RET·transport DRAINED·클라이언트 ACK·실제 표시/효과는 서로 다른 증거입니다.

반증 가능: 현재 bridge가 고른 원 entry가 정상 사용자 동작의 충분한 상위 경계인가, caller가 만들던 입력/등록/분기 조건을 모두 보존하는가, 정상 반환 후 필수 callee/수명 종료가 빠졌는가, 기존 정상 frame/mainloop 소비와 bridge의 역할을 잘못 나눴는가. 특정 null 관측만으로 답하지 말고 기능 전체 경계에서 판단해야 합니다.

## 검토할 대안과 장단점

1. 현 노선을 유지하며 원래 feature entry부터 결과 소비·정리까지 한 묶음으로 복원합니다. 기존 분석/성공을 재사용하기 쉽지만, 실제 상위 caller 경계를 잘못 골랐다면 국소 guard 수정만 누적할 위험이 있습니다.
2. bridge의 entry를 더 높은 원래 UI action/선택 producer로 옮기는 접근을 검토합니다. 원래 코드가 필수 상태를 자연스럽게 생산할 수 있으나, 그 entry의 실제 입력·owner·부작용·once/정리 계약이 확인돼야 합니다. 가짜 event나 dispatcher 중복 호출은 이 대안이 아닙니다.
3. 원래 native 경로는 보존하고 feature-level orchestration과 source-owned 완료 handoff를 명확히 합니다. 입력·원 호출·서버·저장·응답·다음 소비의 상태를 연결하기 좋지만, 실제 producer 없는 상태 머신이나 성공 bool로 원 동작을 대체하면 안 됩니다. 첫 두 대안과 결합 가능한 설계 축입니다.

전면 모사 UI/전체 재작성, guard 삭제, 필드 강제 쓰기, 가짜 성공 응답, 광범위 dump/새 관측 시스템을 기본 대안으로 제안하지 마세요. 현재 노선에서 진전이 가능한지와 어떤 근거가 노선/entry 변경을 정당화하는지 검토해 주세요.

## 요청하는 방향성 판단

1. 현재 원본 기반 클라이언트 + 로컬 서버 노선과 기능 분담은 목표에 맞습니까? 가장 위험한 설계 가정과 먼저 반증할 가정은 무엇입니까?
2. 위 세 접근의 우선순위·장단점·전환 조건을 제시해 주세요. 현 entry에서 계속 복원할 때와 더 높은 원래 entry로 바꿀 때를 어떤 실제 근거로 나눌까요?
3. 다음 한 묶음의 vertical slice를 사용자 동작·원 producer/callee·서버/저장·응답·클라이언트 소비·다음 동작/cleanup까지 정의해 주세요. 기존 성공을 반복하지 않으면서 결과를 가르는 최소 검증은 무엇입니까?
4. 반복 실패에서 미시 분석만 늘어나는 것을 막을 중단/재설계 기준과, 원본 조사 담당·기능 구현·공용 통합 사이의 인계 단위를 제안해 주세요. 함수별 승인/재배정·검토자 증원·관측 도구 확대가 기본 답은 아닙니다.
5. callback null 같은 세부 관측과 Use 완료 수명 결손을 전체 방향 판단의 근거로 어떻게 사용해야 합니까? 원계약과 실제 기능 성공을 증명하지 못하는 외부 정적 의견의 한계도 명시해 주세요.

원하는 답변은 짧은 방향 판단, 우선순위가 있는 다음 작업 묶음, 대안을 바꿀 판정 기준입니다. 주소/ABI/허용 상태를 추측하거나 코드 한 줄 수정으로 답하지 마세요. 저장소 링크를 실제로 열람했는지 먼저 명시하고, 열지 못했다면 이 요약만 읽은 의견임을 명시해 주세요.

기존 `../item-popup-helper-20261020/adapter-control-flow.cpp`는 익명화된 project-authored guard control-flow 예시일 뿐, 실제 제품 source·컴파일/runtime 재현·원인 증거가 아닙니다. 상담의 주 질문은 위 기능 방향성입니다. 기존 좁은 상담은 방향성 검토 완료로 보지 않습니다.
